Harbor & Pine LawExecutive summary

In one page

The site is sound where it counts, and slow where it shows.

Content, accessibility and on-page SEO are in good shape: every page scores 100 on those checks. The problem is delivery. The two pages with photos take 3.6 to 4.8 seconds to show their main content on a phone, well past the 2.5 second line Google uses for ranking signals. The cause is a standard first-pass setup: 18 font weights loaded from Google, icon fonts, 240 to 460 KB photos, and 30 to 38 requests per page where 5 would do. Security basics also need attention: a guessable admin login with a weak password, software versions advertised in the page source, and no backups.

FindingsSpeed and Core Web Vitals

How we measured

Lighthouse 12.8, mobile preset (simulated slow 4G, 4x CPU slowdown), run on October 30, 2026 against all seven public pages. Core Web Vitals thresholds: Largest Contentful Paint (LCP) 2.5 s, Cumulative Layout Shift (CLS) 0.1, Total Blocking Time (TBT) 200 ms. Full Lighthouse reports are attached as an appendix.

01

Full-size photos on the practice-area pages Fail

SpeedLCPEffort S
Found
Two photos were uploaded as 1920 px JPEGs and served at full size: pines.jpg at 457 KB, plus ridge.jpg on the Personal injury page. No responsive sizes, no modern format, no lazy loading.
Why it matters
These are the Family law and Personal injury pages, the ones a search ad or a referral link lands on. On a phone the page's main image appears at 4.8 s and 3.6 s. Google's "good" line is 2.5 s, and visitors on mobile data start leaving well before 4 s.
Evidence
Family law LCP 4.8 s page weight 700 KB Lighthouse: responsive-images savings 405 KB, modern-formats savings 188 KB Personal injury LCP 3.6 s page weight 479 KB Lighthouse: responsive-images savings 212 KB, modern-formats savings 121 KB
Fix
Re-encode as WebP at 1200 px with generated sizes (srcset) and quality 60, set width and height, lazy-load below the fold. The 457 KB photo becomes about 82 KB with no visible loss.
02

Eighteen font weights from Google, plus three icon-font stylesheets Fail

SpeedFCPEffort S
Found
The page builder requests the Newsreader family in every weight and italic (100 to 900) from fonts.googleapis.com, and loads Font Awesome's three stylesheets for the handful of icons in the trust strip.
Why it matters
Every visitor's browser connects to a third-party server and waits for its stylesheet before drawing any text. First text appears at 2.0 to 2.3 s on every page. The firm's headline and phone number should be visible in under a second.
Evidence
fonts.googleapis.com/css?family=Newsreader:100,100italic,200,...,900,900italic (1 external CSS request + font files) Render-blocking resources per page: 16 to 28 (Lighthouse "render-blocking-resources")
Fix
Turn off the builder's Google Fonts option, self-host Newsreader as one variable woff2 (400 to 500) plus one italic file with font-display: swap and a preload. Switch the builder to inline SVG icons so the icon-font CSS never loads.

03

Scripts and stylesheets loading on pages that do not use them Needs work

SpeedRequestsEffort M
Found
jQuery, jQuery Migrate, the builder's frontend runtime and widget chunks, the form plugin's submission script, the emoji script and the block-library stylesheet load on all seven pages. None of the pages use sliders, tabs or popups, so most of it does nothing.
Why it matters
30 to 38 requests per page on a site that needs 4 to 6. Each one is a round trip on a phone connection, and the home page shifts layout (CLS 0.031) while late stylesheets arrive. It also means every plugin update is a chance for something unneeded to break the page.
Evidence
Home: 38 requests, 325 KB, 28 render-blocking, CLS 0.031 Contact: 33 requests, 241 KB, CLS 0.037 Scripts on every page: jquery.min.js, jquery-migrate.min.js, webpack.runtime.min.js, frontend-modules.min.js, frontend.min.js, form-submission.js, wp-emoji-release.min.js
Fix
Remove the parent theme CSS, block-library CSS, icon font, default form styles, jQuery, builder frontend JS and the emoji script on pages that do not need them; set the builder's CSS print method to internal and inline the remaining small stylesheets; add page caching with long cache headers on uploads. Scoped so that adding an interactive widget later re-enables the builder script on that page only.

FindingsSecurity

Eight checks

Security: one check passed, four failed, and all four are cheap to fix.

Checked from the outside and the WordPress dashboard; anything needing server access is marked "not checked" rather than guessed.

CheckResultWhat we sawFix
Administrator account name and passwordFailThe only administrator is "admin" with a weak password; "admin" is the first name every automated attack tries.Create a new administrator with a non-obvious name and a long passphrase, demote and remove "admin".
Login protection (rate limiting, two-factor)FailNo limit on failed sign-in attempts and no second factor.One lightweight login-protection plugin; two-factor for both partners and the assistant.
Software version exposureFailPage source advertises "WordPress 7.1.4" and "Elementor 4.3.5" and appends version numbers to asset URLs.Remove the generator tags and version query strings (a few lines in the child theme).
BackupsFailNo backup plugin or host backup is configured. A bad update or a compromise means a rebuild.Daily automatic backup to off-site storage, 30-day retention, one restore tested and documented.
Plugins installed and currentPassThree plugins (Elementor, Fluent Forms, Yoast SEO), all current, none abandoned or duplicated.Keep as is; add a monthly update routine (see Maintenance).
Contact form protectionNeeds workSubmit requests carry a one-time token (confirmed). The plugin's honeypot and submission limit are available but off, so bots can flood the intake form.Turn on the honeypot and a per-address submission limit (dashboard settings, no code).
XML-RPC and REST user enumerationNot checkedBoth are on by default in WordPress; the live server's setting could not be confirmed from the copy reviewed.Disable XML-RPC unless the firm uses the mobile app; block the users endpoint for anonymous requests.
HTTPS, security headers, file editing in dashboardNot checkedNeeds the live host; checked in the first hour of any fix engagement.Force HTTPS, add standard headers, set DISALLOW_FILE_EDIT.

Why this matters to a law firm specifically

The intake form carries names, phone numbers and a short description of a legal matter. A compromised site can collect those submissions quietly or redirect visitors to a lookalike, with no visible defacement. The four failing checks are the usual path to that outcome; each takes under two hours to close.

FindingsSEO, accessibility, maintenance

SEO

Technical SEO is in order 100 / 100

  • Every page has a unique title and meta description, one H1, a canonical URL and Open Graph tags (Yoast SEO).
  • LegalService and Attorney structured data validate; FAQ markup present on both practice-area pages.
  • sitemap.xml and robots.txt are present and consistent.
  • The one open item is speed itself: page experience signals feed ranking, and two pages currently fail LCP.

Accessibility

Automated checks pass 100 / 100

  • Colour contrast, labels, landmarks, heading order and focus states pass on all seven pages.
  • Form fields are 48 px tall with visible labels and a single focus ring; all controls meet the 44 px target size.
  • Not covered by automation: keyboard walk-through of the mobile menu and the FAQ accordions, and screen-reader reading order. Recommended as a one-hour manual pass after the speed fixes.
